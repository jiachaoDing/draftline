# Architecture

Draftline is one React browser application and one Hono API. SVG is the editable drawing model. AI may produce synchronous HTML/JavaScript to construct it; committed and restored drawings use sanitized SVG snapshots wrapped as HTML. The same API bundles for Node and a Worker.

Browser modules import no Node APIs, provider SDKs or server implementation. Server code imports only universal browser-side contracts. The `DrawingContext` type omits provider settings, while `DrawingRequest` adds them at the transport boundary. Keep DOM-dependent drawing functions in the browser.

`src/lib/i18n.ts` uses i18next and react-i18next for English and Simplified Chinese. English source messages serve as translation keys and fallback text; Chinese UI and common error catalogs live in `src/lib/locales/`. `LanguageSelect` changes the workspace language without remounting the workspace or editor. The workspace defaults to Simplified Chinese, and a valid `draftline-language` local-storage preference restores the explicit selection; storage failure keeps selection usable for the session. Document language/title and CodeMirror phrases follow the selection. Translation at the display boundary leaves project data and source identifiers intact; new blank projects use the selected language for their initial names. Stable translation functions keep switching out of request and persistence effect dependencies.

At each explicit AI submission, App captures the selected language in the optional, validated `DrawingRequest.language` field. This language stays with the active tool loop and pending context; a subsequent explicit continuation uses the current selection. The server adds the response language to system instructions for replies, drawing titles, summaries and questions while preserving JSON keys, tool IDs and measurements. Saved records and API clients can omit the language field. Historical model/user content and existing questionnaire options are rendered as recorded.

Source tool parameter declarations are generated from the universal Zod input schemas using Zod's JSON Schema exporter. `read_source` treats omitted or null optional fields as offset 1, limit 80 and a whole-file read; offsets remain one-based and each read is limited to 200 lines. Argument failures identify invalid fields and bounds, provide a corrective read example and list accepted field names without reflecting unknown keys or argument values. Failed reads preserve the working source and return this feedback to the model for correction.

`configSchema` accepts optional `reasoningEffort`; saved settings default to `auto`. `model-reasoning.ts` resolves automatic GPT-5/GPT-6 and o1/o3/o4 IDs to `high`, including namespaced IDs, and leaves unknown IDs to the provider. Explicit levels take precedence; `provider` omits the parameter. The API sends the resolved `reasoning_effort` in both connection tests and drawing requests. Model configuration stays at the request boundary, separate from credential-free drawing context and project records. The transport uses Chat Completions; gateways serving GPT-6 reasoning with tools must expose that compatible interface.

## Production routing

`wrangler.jsonc` publishes `server/worker.ts` as the Cloudflare API entry and uploads `dist/client` as Static Assets. `/api/*` invokes Hono first; frontend files are served directly by the asset service. `scripts/build-server.mjs` writes `_headers` from `PAGE_CSP`, preserving sandbox policy, privacy headers and immutable caching for fingerprinted assets. It also builds the embedded-assets Node/Worker module used by `npm start` and Sites packaging. The custom domain is `draftline.anxinsm.com`; projects and model settings remain in each browser's origin-scoped storage.

## Generation and manual editing

The drawing workspace arranges the toolbar, document heading, full-size canvas and footer on one surface. The preview iframe is a direct canvas child and fills its bounds; its transparent sandbox exposes the canvas dot grid. The footer owns selection hints, status and zoom controls. Contextual selection and hierarchy controls overlay the canvas, while the source editor occupies the same canvas bounds in Code mode. These display elements leave the canonical SVG and export presentation unchanged.

1. App builds `DrawingContext` with the instruction, optional image, canonical SVG, selected IDs, notes and up to ten completed history messages. Interrupted, validating and review-pending replies are filtered out; history text is bounded to 8,000 characters. Saved single-ID question contexts are accepted by the optional `selectedId` field.
2. App adds settings when calling `api.ts`, which posts `/api/draw`. Hono validates the request. `drawingMessages` constructs system, history, image and tool messages without using settings in their content; the official SDK receives credentials separately.
3. `streamAI` sends `start`, `delta`, `tool_pending`, `result` or `error` SSE events. Bounded `tool_pending` metadata identifies a tool's position/name as its streamed name becomes available; arguments remain private to the tool workflow until terminal validation. Only a successful provider finish and schema validation produce `result`. `previewStream` decodes partial content for plain-text display. Tool-based changes finish with a standalone `finish_drawing` call containing the latest validated revision and a bounded summary. The browser rejects mixed calls, stale completion revisions and unresolved mutation failures; valid terminal JSON messages also pass through the existing completion checks. Ordinary text remains commentary and cannot commit changes.
4. A full drawing becomes a validation candidate. `validateDrawingSource` executes it in a hidden opaque-origin iframe; the parent checks frame source/channel and sanitizes/validates the snapshot. Only then does App commit `{title, summary, notes, svg, html: svgToHTML(svg)}` into history.
5. Existing drawings expose a versioned, formatted virtual `drawing.html`. `runDrawingAgent` repeatedly calls the same streamed `/api/draw` transport, dispatches completed tool calls in order, records exact assistant calls and matching tool results, and requests the next model completion. `source-inspection` uses parse5 locations for numbered source and selected/associated-dimension context. `DrawingToolSession` calls the original Codex Rust WASM engine, then the same opaque-origin sandbox bridge and SVG validation used by previews. Failures become tool results, allowing the model to inspect and retry. Success swaps only the private working version and assigns a fresh revision. A successful terminal completion sends the staged drawing through the commit/review path.
6. Selection and AI scope are separate. `sourceSelectionContext` gives the provider a bounded hierarchy with parent IDs, labels, source ranges and dimensional references. Focused source reads include that structure, so the model can inspect a parent or siblings before editing. Source tools validate and stage coherent changes across the drawing; SVG fragment replacements require existing, distinct, non-overlapping targets with stable root IDs/types and descendant IDs. `drawing-changes.ts` compares actual SVG structure, attributes, text, additions, removals and reparenting while ignoring formatting. App compares those changes with selected objects, their descendants and associated dimensions. Broader changes and metadata changes produce a validated preview with amber outlines and a change list. Apply commits the proposal as one undo step; Discard preserves the committed drawing and excludes the reply from future model context. Generation and manual edits of that drawing are blocked during review; navigation remains available. Proposals are session state; refreshing restores the committed drawing and marks the review-pending reply stopped. Revision guards run before requests, before execution and after asynchronous validation. Cancellation, nonrecoverable failures, unresolved patch failures and the 16-round/6,000,000-character tool-history limit preserve the committed drawing; recoverable model-round failures retain a project-owned continuation point.
7. **Apply code** uses the same cancellable `validateDrawingSource` and project commit path. The editor draft and editor undo are separate from drawing revisions. Formatting completes only into an unchanged draft. Invalid source leaves the committed drawing available.
8. The visible frame receives derived presentation HTML. Layer visibility and pan/zoom are preview state. Exports use the canonical drawing, preserving physical scale; geometry-only export removes dimensions, and dimensioned export derives sheet information.

Cancellation closes the upstream connection and keeps received text for display. `useProjectSession` holds request controllers, reply IDs, validation state, retry context, edit scope and review proposals per project. `useProjectField` creates setters bound to the originating project ID, so callbacks retain ownership across navigation; persistent fields update the existing project record directly. Revision guards compare the originating drawing rather than the visible workspace. Busy remains true through candidate validation, locking only that drawing's mutation actions. Navigation, inspection, pan and zoom remain available. A background commit updates its own history and preserves the visible project's selection and draft. Revision history keeps 30 entries, branching from the active index.

Preview installs its source/channel-checked message bridge in a layout effect during the React commit, before a newly mounted `srcdoc` frame can send its first snapshot. Progress updates and large-reference autosaves must not delay bridge registration beyond frame startup.

`buildSandbox` has validation and interactive modes. Validation runs construction scripts, normalizes object IDs and returns the SVG snapshot. Interactive previews also load pan/zoom and selection libraries. This keeps background validation bounded as projects are navigated. User messages persist the selected IDs alongside their attachments, so explicit retries can recover the original edit scope after refresh.

Project switching and hiding the browser tab keep task controllers alive. Document unload aborts those controllers and flushes all project records; restored unfinished messages settle as stopped.

Canvas fitting skips zero-size frames during hidden views and responsive layout transitions, preserving the pan/zoom transform until the frame has usable bounds.

`svg-selection.ts` owns normalized object selections and reversible group/ungroup operations. Canonical SVG groups and text have stable IDs; `listElements` exposes parent and child IDs without flattening nested objects. `ObjectTree` supplies the resizable, independently scrolling floating hierarchy panel toggled from the canvas toolbar. Canvas selection scrolls the matching row within that panel; row clicks publish the same normalized selection to the frame. `SelectionPanel` provides contextual group actions, selection name/count, grouping status and the editing breadcrumb near the canvas. The AI composer shows a removable selection chip. Grouping siblings uses the topmost selected object's stacking position and preserves member order; intervening unselected siblings remain outside the group. Ungrouping composes transform lists, distributes inherited presentation attributes and rewrites dimension references to group members. Groups with shared compositing effects or references are edited through Enter group to preserve appearance.

`sandbox-selection.ts` installs Viselect's local UMD distribution in the opaque frame for mouse/touch marquee gestures. Marquee selection encloses visible objects at the current group level; Shift adds to it. Click selects the containing object at that level, Ctrl/Cmd-click selects a leaf, and double-click/Enter enters a group. Escape exits one level. Selection uses blue bounding boxes, group isolation a dashed boundary, and proposed changes amber bounding boxes. The frame reports validated `{ids, rootId}` selections through the source/channel-checked bridge, while App filters IDs against the canonical object list. SVG snapshots remove selection markers; overlays live outside the SVG and exports use committed source. Pan/zoom CTM updates refresh overlays without changing object geometry.

App updates project, active-ID and pending-candidate refs at the owning event/effect transition. Rendering does not copy React state back into these refs: an older concurrent render must not overwrite an in-flight project insertion or candidate commit.

`AssistantChat` connects the existing project message list to assistant-ui through `useExternalStoreRuntime`. `chat-runtime.ts` projects messages and attachment parts without a second message store or tool dispatcher. Thread/Message/Composer/Attachment/ActionBar primitives and the Markdown package provide streaming presentation, message copy/retry, multiline input, file removal, drag-and-drop, paste and a jump-to-latest action. `ThreadPrimitive.Viewport` follows streamed content while respecting manual scrolling and only moves its own container. The renderer also handles transient runtime messages while attachments are prepared. The runtime owns the live composer text and attachments. A project-keyed mount restores them once, including under StrictMode effect replay; a layout subscription observes changes for project persistence. Saved project fields never feed back into an already mounted composer. `ChatComposer` reads its controlled value directly from that same runtime through `useSyncExternalStore`: assistant-ui batches its UI projection, which can lag a synchronous project/autosave render and otherwise cause React to write old text into the native textarea during IME composition. The input primitive still owns compositionstart/update/end, Enter/Shift Enter, resizing and file paste behavior. Suggestions explicitly update the runtime; asynchronous examples check both composer identity and draft revision before replacing text. Sending and attachment removal persist through the same observer. Attachment readers use assistant-ui adapters through `CompositeAttachmentAdapter`; the browser preserves original UTF-8 SVG/DXF/text and image/PDF data in existing draft and message records. Uploads allow ten files and 8 MB aggregate, with per-file limits of 4 MB for SVG, 2 MB for text and 8 MB for image/PDF/DXF. Each submitted user message owns its attachments; `projectResources` derives a persistent, deduplicated resource catalog from the originating project's saved records and current submission. A fresh composer starts empty while tools can reuse previously submitted resources. Clarification continuations retain resource IDs and tool results.

The document and React root bound the application to the viewport. App reserves a fixed header and gives the remaining height to shrinkable studio tracks. Desktop panels share one row; tablet keeps navigation full-height beside a bounded canvas/chat split, and mobile stacks the canvas and assistant within the available height. Drawing navigation, chat history, assistant controls and the source editor own their internal scrolling. The assistant controls contain the composer, change review and clarification questions, with enough space reserved for chat history. Responsive rules preserve these size and scroll boundaries when the viewport changes.

`agent-activity.ts` defines portable activity contracts and ordered lifecycle updates. `runDrawingAgent` namespaces activities by model round/tool position and emits pending/running/completed/failed events at actual request and execution boundaries. `DrawingToolSession` reports sandbox validation separately; retry labels require a real patch attempt following a failed patch. App associates events with the active reply immediately, tracks final full-drawing validation through commit, and settles unfinished steps on cancellation/errors. Late events cannot revive terminal steps. `AgentActivities` uses native disclosure controls, compact completion summaries and one polite live status announcement. Only bounded execution metadata and errors, with configured credentials redacted, enter activity history; model reasoning and raw tool arguments are excluded. Activity state persists with messages, defaults for older records and restores unfinished steps as stopped. Model request history still contains only conversation text.

After at least one recorded tool round, recoverable JSON/protocol errors and connection interruptions retry only the failed model round, at most twice automatically. The request carries the current staged source, exact successful call IDs/results and a fixed recovery instruction; rejected response text is excluded. A `DrawingAgentCheckpoint` in the existing originating project session retains validated SVG/canonical source, source inspection revision, mutation failure state, resource snapshot and conversation when retries are exhausted. Continue from failed step reconstructs the same tool session and checks project identity plus committed base revision before sending anything. Duplicate call IDs cannot execute again. Navigation preserves this in-memory checkpoint; cancellation discards it, and refresh restores the transcript as non-resumable. Starting a new request replaces that project's checkpoint. Completion still uses the existing selection review and one bounded history commit.

Response failures carry allowlisted codes and metadata: plain text, invalid escape, incomplete JSON, other malformed JSON, schema/completion mismatch, token limit or incomplete stream, plus character count, optional numeric parse position and terminal finish classification. Activity diagnostics add round/attempt numbers, are capped at 2,000 characters and redact configured secrets. Parser error messages, response excerpts, attachment/source bodies and credentials are excluded from diagnostic records. Authentication, policy and unsupported-tool errors are not automatically retried.

## Clarification and persistence

`request_user_input` calls contain validated JSON arguments and stable tool IDs. `PendingUserInput` stores original context, the assistant request, current call index, submitted responses and questionnaire drafts. `answerQuestions` advances queued calls, then builds one tool turn in call order. It leaves pending state unchanged for a failed/stopped continuation to retry. Up to 12 rounds are accepted. The server recreates each assistant `tool_calls` message and matching `tool_call_id` result. Text clarification also retains original context and appends the user's measurement.

Tool instructions require concrete, directly usable predefined answers; an empty options array supports exact measurements without suggested values. The client adds one custom-answer choice identified by its position after the model options, independently of label text. Each answer stores a separate `customAnswer` draft (defaulting to empty for saved records) and optional `notes`. Mouse, arrow and numeric selection immediately focus the custom textarea; navigating back to that question restores its text and focus. Submission requires non-whitespace custom text. `collectAnswers` returns either the predefined label or trimmed custom text, plus optional `user_note: ...`; invalid or uncommitted answers return empty arrays. Skip and unanswered confirmation preserve explicit submission. Textarea arrow keys retain native caret movement; PageUp/PageDown and Ctrl P/N navigate questions.

Source tool rounds carry their question-round index, preserving their ordering with clarification messages across retries and refreshes. Questions are requested before source mutations. The pending context stores inspection/error rounds and the committed source identity; staged mutations belong to the originating project session and its continuation point. Mixed source/question batches receive corrective tool feedback. Settings are added only at the API boundary.

`Project` stores name, revision history/index, conversation/message attachments, composer text/attachments, clarification/question state and layers in IndexedDB through `idb`. Saves batch streamed deltas per project at 400 ms and flush all project records on page hide. Active project ID lives in a separate metadata store. Restoring a record validates/sanitizes its SVG, rebuilds HTML, and marks interrupted replies cancelled. Invalid records remain stored and produce a warning; storage errors keep the workspace usable and show an error notification. Successful background saves do not change the header or display a saving indicator.

An empty project store initializes four curated projects named 样例1 through 样例4, with matching drawing revision titles, from the lazy-loaded `starter-projects.json` in one IndexedDB transaction. The data contains canonical SVG revision snapshots, original references and completed conversation/tool steps. Failed or cancelled replies, failed tool attempts, retry-only prompts, source-code transcripts and unsent drafts are excluded. The normal project schema validates and sanitizes every sample before persistence. Existing records are restored without adding samples; a valid `draftline-drawing` record is imported as its own project. Samples remain ordinary editable, renameable and deletable projects.

Model URL/key/ID live in the `draftline-model` local-storage entry. Project serialization lists fields explicitly, and schemas strip extra fields. Source scripts are not replayed from stored projects. Changing a project remounts `ProjectList`, resetting its rename/delete UI.

`DrawingSidebar` owns name search and responsive navigation, using a single scrolling drawing list ordered by creation time, newest first. Projects persist an immutable `createdAt` alongside `updatedAt`; restoration initializes a missing creation time from the saved update time. Opening, editing and renaming preserve the creation time and list position. App owns the sidebar's collapsed state and grid width. On mobile, Headless UI Dialog supplies drawer focus trapping, Escape/outside dismissal and focus restoration; navigation runs after the drawer's exit transition so the new workspace can focus its own inputs. Search survives project switches; creating a drawing clears it. `ProjectList` uses Headless UI Menu for keyboard-accessible rename/delete actions and Dialog for deletion confirmation. Blank projects choose an available numbered name from the workspace. `DrawingLayers` uses a Headless UI Popover beside the canvas tools; its checkboxes update the same per-project preview visibility state.

## Project resource tools

Storage, request context and tool output have separate limits. `runDrawingAgent` snapshots resources from the originating project's records, keeps the source bytes local, and sends metadata for the first 100 entries. `list_resources` pages through the full permitted catalog in batches of 30. Resource IDs resolve only against that request's project snapshot; the API has no resource URL, global lookup or filesystem access. Browser-origin/profile storage is the user ownership boundary. Deleting a project deletes its stored resources with the same IndexedDB record.

`inspect_resource` returns metadata and can attach a requested visual preview. SVG/image previews are rasterized locally to at most 1024 pixels per side. PDF.js runs in a same-origin module worker, renders one explicitly selected page and extracts page-wise text; original PDF bytes stay in the browser. The parent CSP permits same-origin workers; drawing frames keep workers and network blocked. Previews use bounded image data in validated agent turns, reconstructed as user image parts after the matching tool results. `read_resource` reads/searches literal UTF-8 text with zero-based character offsets and at most 12,000 characters; serialization also stays below the tool-result budget, including control characters. PDF offsets apply to the selected page's extracted text. The tool conversation has a 6,000,000-character aggregate budget, separate from the 12 MB API body limit.

`place_svg` inserts the sanitized vector resource inside a named geometry group, preserves its viewport/aspect ratio, namespaces IDs and rewrites internal fragment references. CSS Tree and Specificity resolve supported static presentation CSS into SVG attributes. DOMPurify removes executable content, external references and raster dependencies; gradients, clipping, masks, safe filters and local `use` references pass through the same drawing sanitizer and export path. The original resource remains intact in storage. `transform_object` applies an incremental translation/rotation/uniform scale in drawing coordinates without rewriting paths. Synchronous native SVG matrix operations in the validation sandbox account for transformed parents and nested viewports for placement and transformation. Imported SVG roots receive standalone presentation defaults to isolate them from drawing styles. Both tools stage changes through `DrawingToolSession`, require the current drawing revision, run sandbox validation, and enter the existing selection-review and bounded history path only after terminal success. On a blank project `place_svg` requires explicit canvas dimensions; missing essential measurements go through the existing question flow.

`place_svg.bounds` is required: `content` scales measured artwork, while `canvas` scales the complete resource viewport including whitespace. Width is in drawing millimeters before optional rotation. `anchor:origin` (also omitted/null) maps the content bounding-box top-left or canvas origin to `x/y`; `anchor:center` maps the corresponding center there. Rotation is about that anchor. Full-canvas placement uses `bounds:canvas` explicitly. `fit_box` supplies a part's available rectangle in drawing coordinates; content placement otherwise checks the drawing viewBox. A requested size that exceeds this area fails without reducing the width. The tool does not infer plate interiors or manufacturing clearances from arbitrary geometry.

`svg-placement.ts` follows the [native SVG bounding-box contract](https://www.w3.org/TR/SVG2/coords.html#BoundingBoxes) and the mounted-clone approach used by [SVG.js](https://github.com/svgdotjs/svg.js/blob/master/src/types/Box.js). The existing opaque validation frame receives layout before construction. Placement runs synchronously in the document's DOMContentLoaded handler, before the window bridge takes its snapshot. A temporary attached measurement group includes the resource viewport and transforms; hidden/unpainted geometry is removed only from this measurement copy. Native `getBBox()` supplies geometric content bounds, and native screen matrices map the uniform placement transform through drawing parents. Paths and definitions in the placed resource remain intact; temporary measurement nodes are removed before validation. The original resource bytes stay in project storage.

Native bounding boxes are geometric, not pixel-alpha bounds. [Browser compatibility data](https://github.com/mdn/browser-compat-data/blob/main/api/SVGGraphicsElement.json) records that Chromium/Edge do not support `getBBox` stroke/clipping options. The supported content subset therefore includes filled paths/basic shapes, opaque gradients, solid axis-aligned rectangle/circle/ellipse strokes with absolute widths, and enclosing unrounded rectangular user-space clips/viewports. The stroke extent is added only to the temporary measurement copy. Intersecting/rotated clips, slice viewports, masks, filters, markers, patterns, transparent/indirect gradients, text/use instances, non-scaling/dashed/path/rotated strokes and parent compositing effects return explicit measurement errors. Conservative containment checks may reject nested viewports with unrelated siblings. Canvas placement preserves these definitions and their layout without promising content bounds. Canvas-covering background/artwork ambiguity requires `target_id`, an original resource element/group ID; other rendered branches are hidden in that instance, preserving its ancestor styling and definitions. No automatic background removal or guessed path bounds occur.

The editable drawing/source capacity is 600,000 characters, independently of resource upload capacity. A resource can be stored, inspected and paged even when its complete vector content exceeds the canvas capacity; placement returns bounded feedback without changing the drawing. SVG processing bounds element and stylesheet complexity. The open-source dxf parser runs in a cancellable, time-limited worker for DXF entity metadata and geometric previews; text, dimensions, hatches and unsupported entities may be absent from the overview. Exact DXF sections remain available through literal searches and segmented text access. PDF rendering uses built-in vector font rendering and system fallback fonts; documents requiring additional CMaps, specialized codecs or external font assets may return rendering feedback.

## Decisions and remaining risks

- Keep React state in the coordinator where preview, assistant and persistence share it; keep focused transient UI state inside components. Pure workflow functions improve testability without a second state store. App still coordinates autosave and asynchronous request/validation state: extract a project hook or reducer only when a concrete change needs it, with switching/retry/storage tests first.
- Zod, DOMPurify, Hono, the official SDK, `idb`, CodeMirror, Prettier and existing stream libraries own their specialist work. Biome handles targeted correctness/hooks/import checks; TypeScript checks types and Prettier owns formatting. Hook dependency checking permits event-trigger dependencies such as refocusing on a question change and allocating a new frame channel per source.
- Generated code must finish synchronously. The iframe/CSP isolates origin access and network, but cannot enforce a CPU quota; an infinite script can block the browser. Future execution isolation requires a separate design and browser tests.
- SVG validation proves structure, scale and dimensional references, not that geometric relationships match the requested part. Treat output as user-reviewable drawings; a future geometric checker should target specific constraints rather than introduce a speculative CAD kernel.
- Provider URL validation blocks literal private addresses and unsafe URL forms. It does not resolve DNS or enforce redirect/network egress policy. Public multi-user hosting needs platform-level egress, authentication and usage controls before broad exposure.
- Browser-origin storage is the workspace's persistence boundary. Large histories/images and conversations can grow storage use; quota warnings and export exist. Repeated image storage and retention policies are a future measured improvement.
- Packaging embeds frontend files as UTF-8 text. The Rust WASM payload is base64 in a lazy JS chunk, so the same frontend artifact works with Node and Worker hosting. The parent CSP explicitly permits WASM compilation; each drawing iframe retains its nonce-only script policy. Build-source and artifact hashes detect an out-of-date patch binary.
- The production build reports frontend chunks above 500 kB after minification (the main application and lazy CodeMirror editor). Measure load/interaction costs before adjusting chunk boundaries; browser validation is needed for any lazy-loading changes.
